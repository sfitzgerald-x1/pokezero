## Exact chance and GPU ownership

`phase_d_chance` retains the existing conservative finite-chance consumer
program unchanged. Its explicit current source/domain pins are separate from
the old fidelity consumer's unchanged pins. Advancing pins is not evidence of
fidelity: the producer review must inspect the current transition/secondary

`phase_d_search.Search` requires exactly one visible GPU and the real 9375
champion archive/checkpoint binding. It prices every legal action and every
legal reply (from all nine request slots), then every positive exact chance
case, before reply-policy and world averaging. It chooses the best averaged Q,
with the lower action index breaking ties. Missing worlds, replies, chance mass
or leaf outputs refuse; there is no surviving-branch renormalization. The cap
bounds both each law and the complete decision's chance branches. The initial
source uses at most 262,144 exact branches per request and 4,096 GPU lanes.

One `phase_d_search_server.Server` batches concurrent CPU panel requests, has
one queue consumer and one executor thread, and shares one retained evaluator.
The real GPU forward and mapped transition batches combine worlds/branches
from concurrent requests. `phase_d_panel_actor.factory` preserves original B2
encoding/choice routing and sends only its own snapshot to that server. It
runs no CPU inference. The current adapter is explicitly bound to 9375; a
future winner needs its explicit evaluator/actor contract rather than silently
being treated as champion.
